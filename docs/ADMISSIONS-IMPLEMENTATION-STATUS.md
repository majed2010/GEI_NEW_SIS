# Admissions implementation status — 1 October 2026

The authenticated Arabic RTL admissions module now includes student search and filters, paged results, a five-section add/edit form, detail view, photo display/upload, print, and supervisor-only archive/restore. Its ASP.NET Core API uses the existing `dbo.Students` aggregate and explicit lookup queries. Student codes are designed to use the configured `ActiveSemesters.AdmissionYear`, `Years.ActualYear`, and `ActiveSemesters.AdmissionsSemester`; the staff form does not choose the insertion semester. Create, update, and archive use SQL transactions, audit records, idempotency for creation, and rowversion checks. Permanent deletion is not offered.

**Admissions edits and new-student creation are enabled on this TeiDB.** On 1 October 2026, after confirmation that TEIADMIN student writes were stopped, a copy-only database backup was created and verified at `database/backups/TeiDB-before-admissions-20261001-102052.bak`. The support schema and cutover scripts were then applied with their activation guards enabled in memory; the checked-in review files still default to no operation. The active settings were `AdmissionYear = 27`, `Years.ActualYear = 2026`, and `AdmissionsSemester = 66` (a visible semester in year 27). All 4,687 existing student codes were unique, and none matched the `2026` plus four digits pattern. The global unique student-code index was created and `sis.StudentCodeCounter` was seeded with `YearPrefix = 2026`, `LastAllocated = 0`. The user-configured `Admissions:WritesEnabled = true` remains in place. The live LocalDB smoke reports `canWrite=True` and `canCreate=True`, reads all 15 lookup lists, searches 4,687 students, and opens a student detail with seven related sections. The local API was restarted and its health endpoint responds. Save, archive, restore, and photo upload have not been exercised against real student data.

The applied SQL came from the [support schema proposal](../database/review/001-admissions-support-proposal.sql) and [counter/uniqueness cutover proposal](../database/review/002-admissions-cutover-proposal.sql). Both files remain guarded and should not be run again as migrations. Assign the `Admissions.Supervisor` Entra app role to supervisors for archive/restore. Keep TEIADMIN student writes stopped so its code allocation cannot diverge from the new counter. Admissions staff can now add and edit students through the SIS.

Legacy images are read from `Admissions:LegacyImageRoot`; new images are stored in `App_Data/admissions-photos` outside the web root and served through the protected API. Configure the legacy directory path when deploying to another machine. The image handler checks type signatures, size, and header dimensions; a full image decoder or image-processing service would provide stronger content validation if production policy requires it. Existing student lists currently show all non-archived students by default so records are not silently hidden by an unapproved “new student” predicate. Staff can narrow by year, status, and other filters. Archive state currently affects this admissions API; downstream registrar, finance, and legacy workflows will need to honor it after cutover.

Run the frontend with `powershell -ExecutionPolicy Bypass -File scripts/start-frontend.ps1` from the repository root. The backend uses `dotnet run --project backend/Gei.Sis.Api`. The read-only integration check is `dotnet run --project scripts/AdmissionsReadSmoke` under the Windows account that owns `(localdb)\MSSQLLocalDB`.
